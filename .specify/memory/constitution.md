# Advanced Analytica IBOM Stack Constitution

This constitution defines the non-negotiable architecture, delivery, security,
continuity, and governance controls that apply to every Advanced Analytica build using
this stack. It MUST contain only requirements intended to remain true across
engagements. Client-specific requirements, feature behaviour, recovery targets,
deployment sizing, commercial constraints, and implementation decisions MUST be
recorded in client overlays, specifications, plans, architecture decisions, and task
lists instead. A proposed rule belongs in this constitution only when failure to apply
it would materially weaken the integrity, security, auditability, maintainability, or
operational continuity of every build.

Working terms used throughout: **product repositories** are the three repositories
containing runtime product code or canonical database migration history; the
**governance repository** stores canonical constitutions, presets, client overlays,
approvals, and governance material and is excluded from that count; the **canonical
constitution** is the approved, versioned source copy; the **resolved constitution**
combines it with an approved client overlay and is placed in each product repository;
**governance data** comprises the asset register, audit log, record of processing
activities, data-classification records, breach log, incident log, and feature-request
log; a **substantive action** modifies code, configuration, data, infrastructure,
external systems, GitHub state, deployment state, or an approved delivery artifact; a
**waiver** is formally approved, time-limited authority to deviate from a requirement;
a **break-glass action** is an emergency administrative action needed to protect
service availability, security, safety, or data integrity.

## Core Principles

### I. The Product Repository Boundary Is Fixed

The stack MUST use exactly three product repositories:

1. `backend-processing`
2. `frontend-workspace`
3. `supabase-config`

The organisational governance repository, including `stack-constitutions`, is excluded
from this count because it does not contain runtime product code.

`backend-processing` MUST own Python application services, data processing, business
logic, integration logic, database access code, and backend API behaviour.

`frontend-workspace` MUST be a Turborepo monorepo containing the Astro website, Next.js
application, chat interface, and shared UI packages.

`supabase-config` MUST own the canonical Postgres schema history, Alembic migration
files, migration ordering, migration validation, and migration execution configuration.
It MUST NOT contain general application business logic. SQLAlchemy models in
`backend-processing` MUST conform to the canonical schema but MUST NOT establish a
second migration history.

A feature affecting more than one product repository MUST use one shared feature
identifier and separate repository-local plans and task lists. Every task MUST have one
owning product repository.

Permanent changes to repository count or responsibility require a MAJOR amendment.

Each of the three product repositories' `main` branch is the canonical governance
template and MUST remain a working, deployable default build. Client-specific
development MUST NOT occur on a branch within a product repository's own history.
Instead, each new client engagement MUST begin with a physical fork, one new
repository per product repository, cloned from that repository's current `main`.

A client's three forked repositories (backend-processing, frontend-workspace,
supabase-config) MUST be tracked as a linked set under the client's name, even though
git itself does not enforce that link. Each forked repository MUST establish its own
protected `main` and follow this constitution unchanged, unless a documented client
overlay states otherwise.

Client repositories MUST NOT merge into, or open pull requests against, the origin
product repositories. Promotion to a client's production environment MUST occur by
continuing development within the client's own forked repositories, never by merging
client work back into origin. This isolates every client engagement from every other,
and keeps the origin repositories permanently reusable as the starting point for the
next fork.

**Rationale:** A fixed boundary prevents competing schema histories, creates accountable
ownership, and limits the blast radius of automated changes. Physically forking each
client engagement, rather than branching within the origin repositories, removes any
possibility that one client's work is accidentally merged into another client's
repository or into the reusable origin template.

### II. Postgres Is the Governance System of Record

Postgres, operated through the approved Supabase deployment, MUST be authoritative for
all governance data.

Dashboards, GitHub issues, exports, caches, reports, and integrations MAY mirror that
data but MUST NOT silently supersede Postgres. Where a mirror disagrees with Postgres,
Postgres wins unless an authorised integrity investigation confirms corruption.

Application access MUST pass through a documented, validated service or repository
layer. Supabase convenience APIs MAY be used but MUST NOT become the sole path to core
governance data.

Every synchronised surface MUST use stable identifiers, idempotent updates, bounded
retries, failure logging, and periodic reconciliation.

**Rationale:** Governance records remain trustworthy only when one authority determines
their state and all secondary surfaces can be reconciled.

### III. Main Is Protected and Every Change Is Reviewable

The default branch in every product repository MUST be protected from repository
creation. Direct pushes, force pushes, and branch deletion MUST be disabled. Routine
changes MUST enter through pull requests.

A pull request MUST NOT merge unless all required checks pass, its branch is current,
at least one authorised review or approved equivalent control is satisfied, unresolved
conversations are resolved, and the change has an accountable owner.

Branch protection MUST NOT be weakened for routine delivery. Break-glass bypass MUST be
restricted to named roles and MUST produce an incident record, linked issue, reason,
authoriser, changed scope, timestamp, and retrospective review.

**Rationale:** Protected, reviewable change is the enforcement mechanism behind all
other principles.

### IV. CI Passing Means the Change Is Verified

A green CI result qualifies a pull request only when all checks applicable to the
affected boundaries have run and passed.

Applicable CI MUST include formatting and linting, type checking, unit or component
tests, integration or contract tests, build verification, schema and migration
validation, static application-security testing, dependency analysis, secret scanning,
and constitution-version validation.

Testing MUST be based on requirements, contracts, risk, and changed behaviour. Every new
or materially changed endpoint MUST test its contract, authentication, authorisation,
validation, success paths, and relevant failure paths.

Every package containing testable application logic MUST maintain at least 80% line
coverage. Coverage MUST be measured per repository or declared testable package.
Generated code, vendored code, migration files, type declarations, and declarative
configuration MAY be excluded only through version-controlled configuration.

Every pull request MUST report total applicable coverage, the coverage delta, untested
material behaviour, and approved exclusions or waivers.

**Rationale:** Branch protection is meaningful only when passing represents a defined,
inspectable verification standard.

### V. Every Task and Governance Trigger Is Traceable

Every approved Spec Kit implementation task MUST correspond to a GitHub issue or
approved tracked child item. Every actionable incident, breach, and approved feature
request MUST create or update a corresponding issue unless that would expose restricted
information; in that case the issue MUST contain only a sanitised reference.

Tasks MUST use this globally unambiguous identifier:

`{feature-id}:{repository}:{task-id}`

Issue synchronisation MUST be idempotent and MUST include retries, failure logging,
manual recovery, periodic reconciliation, ownership, bidirectional links, and an audit
trail. Sensitive issues MUST NOT contain credentials, unnecessary personal data,
restricted exploit details, or confidential client information.

**Rationale:** A governance signal has operational value only when it reaches a
monitored execution surface without exposing the protected record.

### VI. Authoritative Context Must Be Restored After Context Loss

After compaction, compression, reset, suspected context loss, or transfer to a new agent
session, the agent MUST perform no substantive action until it has reloaded the resolved
constitution, current specification, plan, tasks, active task state, relevant design
artifacts, architecture decisions, and unresolved waivers or review comments.

A compressed summary MUST NOT substitute for source documents. After reloading, the
agent MUST restate the active feature and task, owning repository and package,
constitutional gates, known risks or waivers, and next permitted action.

**Rationale:** Explicit recovery prevents architectural drift, duplicated work, missed
controls, and unauthorised action.

### VII. Security Controls Are Enforced

MFA MUST be enforced for human interactive access to GitHub, Supabase administration,
DigitalOcean, production administration, and other privileged management surfaces.
Customer MFA MUST be determined by risk, contract, and client overlay.

Customer-facing authentication method (password, magic link, OAuth, or a combination)
MUST be selected per build in the plan, based on risk, contract, and client overlay.
Magic-link authentication MAY be used as a default customer authentication option
where email-address ownership is an adequate identity signal for the data involved.

Any build operating in prototype, pilot, or pre-production status MUST gate its
customer-facing authentication flow on active acceptance of Advanced Analytica's
standing prototype and pilot disclaimer before an authentication credential (a magic
link or equivalent) is issued. Acceptance MUST be an explicit action, not implied by
continued use, and MUST be logged with a timestamp, the accepted disclaimer version,
and the accepting identity. The disclaimer MUST be a single AA-wide policy referenced
by every prototype or pilot build rather than drafted per client or per engagement,
and MUST state the build's non-production status, that availability, retention, and
security are not guaranteed to production standards during this phase, and the
categories of data the build processes. This disclaimer governs use expectations and
liability only; it MUST NOT be represented as satisfying UK GDPR lawful basis,
retention, or security obligations, which apply in full regardless of prototype
status.

Machine identities MUST use least privilege and SHOULD use short-lived credentials or
workload identity. Secrets MUST never be hardcoded, committed, logged, or placed in task
descriptions. `python-dotenv` MAY be used locally only; production secrets MUST use an
approved secret store or encrypted platform configuration.

Externally reachable endpoints MUST apply appropriate authentication, explicit
authorisation, validation, abuse protection, secure errors, and security audit logging.
Authentication MUST NOT be treated as proof of authorisation.

Critical and high findings MUST block merge unless covered by an approved, unexpired
security waiver. Logs and issues MUST minimise personal data and exclude secrets.

These controls support security and compliance readiness but MUST NOT be represented as
proof of certification or complete regulatory compliance.

**Rationale:** Security depends on enforced identity, pipeline, coding, and operational
controls rather than product defaults or developer memory.

### VIII. Continuity Is Defined, Owned, and Tested

Every production build MUST document its RTO, RPO, backup scope and schedule, retention,
recovery dependencies, service owner, incident-response runbook, recovery procedure,
and escalation path.

Client-specific RTO and RPO values MUST be approved before production launch. Provider
backup claims are insufficient without documented scope, retention, ownership, and
recovery steps.

Restore procedures MUST be tested at least annually, after material backup changes, and
at any shorter interval required by risk or client overlay. Each exercise MUST record
scope, owner, source, achieved recovery time and point, failures, remediation, and
evidence. Material failures MUST create a remediation issue.

**Rationale:** Backups and runbooks provide assurance only when their scope is known,
owners are accountable, and recovery is demonstrated.

### IX. Model Provider Calls Are Routed Through an AI Gateway

Application code MUST NOT call AI model provider SDKs or APIs directly from
application services. All calls to AI model providers MUST route through a single
approved AI gateway per build.

The gateway MUST log, per call, the token usage, cost, latency, provider, and model
identifier. It MUST support key rotation, per-environment key isolation, and rate
limiting. It MUST provide a single point at which provider access can be revoked or
throttled without an application code change.

The gateway MAY be a managed product, such as Cloudflare AI Gateway or Vercel AI
Gateway, or a self-built internal service, selected per build through a documented
architecture decision. Equivalent or stronger implementation tools MAY replace named
products where the required logging, isolation, and control surface remain intact.

**Rationale:** Centralised, logged, revocable access to model providers is the same
governance discipline this constitution already requires for data and code, applied to
AI traffic; direct SDK calls from application services make usage, cost, and provider
exposure ungoverned and unauditable.

### X. Every Feature Is a Tracked, Estimated Milestone

Every Spec Kit feature MUST be created as a GitHub milestone in its owning product
repository at the point the feature is specified, before planning or task generation
begins. The milestone title MUST match the feature's Spec Kit identifier.

Once tasks are generated for a feature, the Spec Kit tasks-to-issues conversion MUST
run automatically as part of that generation step, not as a separate manual action.
Every resulting GitHub issue MUST be attached to that feature's milestone at creation
time. No task issue MAY exist without an owning milestone, and no milestone MAY remain
without its task issues once tasks.md exists for that feature.

Every milestone MUST carry a three-point human-effort estimate, best case, most
likely, and worst case, expressed in hours, using a named and consistently applied
estimation technique. This estimate MUST be recorded at milestone creation as its own
task issue, distinct from implementation task issues, and closed only once the
milestone's actual elapsed effort has been compared against it and the resulting
variance recorded on the milestone. A milestone MUST NOT be closed while its
estimate-and-reconciliation issue remains open. Estimates MUST be treated as a
reviewer aid for cost and planning purposes, not as a committed delivery time or a
contractual figure.

Every task within the milestone MUST carry its own three-point human-effort estimate,
low, likely, and high, expressed in hours, plus the likely cost at the repository's
default hourly rate. Per-task cost estimates MUST appear in the task list and in the
corresponding task issue body when issues are created. The milestone's own estimate
MUST reconcile against the sum and outcome of the task-level estimates during
closeout, so cost variance can be traced to individual tasks rather than only to the
feature total.

A running build-economics document MUST be maintained per product repository,
tracked in that repository's docs. It MUST contain, at minimum:

1. A completed-features table, one row per closed milestone, giving task count, summed
   task-level low, likely, and high estimated hours, likely days, and likely cost at
   the repository's default hourly rate, with a completed-total row summing every
   column.
2. A planned-features table in the same shape for specified but not yet closed
   milestones, kept separate from the completed total.
3. A milestone-definitions table giving one plain-language row per milestone
   describing what was actually delivered, so the estimate table can be read
   alongside real scope rather than titles alone.
4. A cost-sensitivity table showing low, likely, and high total cost across at least
   three hourly-rate bands.
5. An agent-assisted time and savings section recording actual agent-assisted elapsed time
   against the human-effort estimate wherever a reliable elapsed-time anchor exists.
   Where no reliable anchor exists for a milestone, that MUST be stated explicitly;
   a missing anchor MUST NOT be backfilled with an invented or estimated figure.
6. A GitHub reconciliation record confirming milestone, parent-issue, and task-issue
   counts match, and the closeout comment format used on every closed feature's
   parent issue, which MUST carry the feature definition, delivered scope, outcome
   evidence, tracking state, the estimate and likely cost, and the pre-screening or
   equivalent safety boundary applicable to that build.

This document is for internal use and MUST NOT be shared externally without the same
commitment disclaimer required of individual milestone estimates.

**Rationale:** A feature without a milestone cannot be costed or reported on; a task
issue without a milestone cannot be traced back to the feature it serves; and a task
without its own cost estimate cannot explain where the milestone estimate came from.
Making the estimate-and-reconciliation step its own closing task issue ensures it is
never skipped or forgotten once implementation work is done. Recording and reconciling
a three-point estimate against actual effort at every milestone closure, and
aggregating that into a running, honestly-anchored build-economics document, is what
allows estimation accuracy to improve build over build while giving a clear internal
view of the value agent-assisted delivery is generating, without overstating savings
the data does not actually support.

## Default Platform Profile

- Backend: Python, SQLAlchemy, Pydantic, Pytest, Ruff, Mypy, uv.
- Migrations: Alembic history and execution owned solely by `supabase-config`.
- Frontend: Turborepo, Astro, Next.js, TypeScript, shared `ui` package.
- Database: Postgres through Supabase, with service/repository-layer access.
- Hosting: DigitalOcean by default for application workloads and Supabase for Postgres.
- Object storage: DigitalOcean Spaces by default, for consistency with the hosting
  provider. AWS S3 or Azure Blob Storage MAY be used where a documented architecture
  decision justifies it. Object storage MUST NOT become a secondary source of truth for
  governance data; where governance-data files are stored as objects, Postgres MUST
  retain the authoritative record and reference.
- AI SDK: the Vercel AI SDK MAY be used as the default application-layer client for
  calling the approved AI gateway required under Principle IX, on the grounds of
  provider-agnostic design, gateway compatibility, and maintained TypeScript support.
  An equivalent or stronger SDK MAY replace it through a documented architecture
  decision; it MUST still route all calls through the approved gateway and MUST NOT
  be used to call model providers directly.

Equivalent or stronger implementation tools MAY replace named tools through a documented
architecture or security decision when the required control and evidence remain intact.

External products and platforms remain outside this constitution and MUST be integrated
through documented interfaces.

## Governance Data and Delivery Controls

The seven governance-data categories are the asset register, audit log, ROPA,
data-classification records, breach log, incident log, and feature-request log.

- Asset records MUST include accountable owner, technical owner, purpose, environment,
  classification, lifecycle state, and relevant relationships.
- Sensitive governance tables MUST have an access-controlled, append-oriented audit
  trail identifying time, actor, action, record, source, and sufficient change detail.
- Personal-data tagging MUST create a draft ROPA assessment. Purpose, lawful basis,
  subjects, recipients, transfers, retention, processors, and security measures require
  authorised human review.
- Sensitive classifications MUST trigger assessment of DPIA, security, contractual, or
  other risk processes; the trigger does not predetermine the outcome.
- The breach log MUST record awareness time, risk assessment, decision owner,
  reportability decision, reasoning, deadline, actual notification time where required,
  affected-person communication, containment, and reasons for delay or non-notification.
- The incident log MUST record operational, security, availability, and integrity events
  and require a recorded outcome and residual risk at closure.
- Approved feature requests authorise specification preparation, not implementation.

**Specification Gate.** Specifications MUST define required behaviour and rationale
without selecting source files, packages, repositories, migration mechanisms, or
deployment implementations. They MUST identify user or business impact, acceptance
criteria, governance-data impact, privacy and classification impact, security and
identity impact, audit needs, continuity impact, dependencies, assumptions, and risks.

**Planning Gate.** Plans MUST identify the owning repository, affected package or
service, interfaces, migration authority, deployment target, security controls, test
strategy, governance-data effects, continuity effects, and rollback or recovery
approach. Cross-repository features MUST have a coordinating parent plan and separate
repository-local plans. A Constitution Check MUST occur before research and after
design. Conflicts MUST be resolved by redesign, an approved temporary waiver, or
constitutional amendment. Complexity Tracking documents complexity but MUST NOT
authorise a violation.

**Task Gate.** Task lists MUST be repository-local. Every task MUST include a
composite identifier, owner, boundary, expected output, validation, dependencies,
linked issue, low/likely/high human-effort estimate, likely cost, and completion
evidence. Verification tasks MUST precede corresponding implementation tasks where the
workflow requires test-first delivery.

**Implementation and Release Gates.** Implementation MUST follow the repository-local
plan and tasks. A feature MUST NOT be claimed complete when required verification has
failed. Release requires passing CI, resolved or waived high findings, validated
migrations, operational documentation, approved RTO/RPO, rollback or recovery steps,
matching constitution version and hash, and retained evidence.

## Exceptions and Constitution Distribution

Permanent weakening or incompatible redefinition requires amendment. Temporary
deviation requires a written waiver containing the affected clause, scope, reason, risk,
alternatives, compensating controls, owner, approvers, issue, start date, expiry, and
remediation plan.

Waivers MUST expire within 30 days unless a shorter period is required, MUST NOT renew
automatically, and MUST NOT authorise credential exposure, falsification or silent loss
of governance data, unlogged audit deletion, unauthorised data access, permanent branch
protection removal, routine unreviewed production changes, or concealment of incidents.

Break-glass action MAY precede paperwork only where delay creates greater immediate
risk. It MUST be recorded no later than the next business day and retrospectively
reviewed.

The canonical constitution MUST be versioned in the governance repository. Each release
MUST have a semantic version, immutable tag or release identifier, content hash,
approval record, Sync Impact Report, and effective date.

Each product repository MUST contain the resolved constitution at
`.specify/memory/constitution.md` and a machine-readable governance lock recording the
constitution version and hash, client overlay version and hash, resolution date, source
release, preset version, and repository identity.

CI MUST reject missing, invalid, stale, or inconsistent governance state. Project-local
template overrides MUST be empty unless explicitly approved and hash-locked.

Client overlays MAY add values, stricter controls, contractual requirements, recovery
objectives, retention periods, and named owners. They MUST NOT silently weaken this
constitution. Canonical updates MUST be explicitly propagated and re-hashed.

## Governance

Amendments MUST be approved by the Constitution Owner, Platform Architecture Owner,
Engineering Quality Owner, and any materially affected control owner. Security changes
also require the Security Owner; personal-data changes require the Data Protection
Owner.

**This Constitution Supersedes the Spec Kit Default.** The `specify init` command, or
any equivalent Spec Kit initialisation command, generates its own placeholder
constitution file as part of a fresh installation. That generated file MUST NOT be
kept, edited into, or merged with this document under any circumstance. Immediately
after running Spec Kit initialisation in any product repository, whether an origin
repository or a client fork created under Principle I, the generated constitution file
MUST be deleted or fully overwritten with the current canonical version of this
document before any specification, plan, or task work begins. No specification, plan,
task, or agent session MAY treat a Spec Kit default constitution as authoritative. This
document is the only valid constitution for any repository governed by it, regardless
of what Spec Kit's own tooling generates.

Every amendment MUST include a Sync Impact Report, semantic-version rationale, ISO
dates, affected templates and runtime guidance, rollout work, unresolved follow-ups,
approvals, release identifier, and content hash.

**Versioning Policy:**

- **MAJOR**: incompatible redefinition, principle removal, permanent weakening, changes
  to the three-product-repository boundary, Postgres governance authority, the waiver
  model, or the document's own structural skeleton.
- **MINOR**: new principles, mandatory controls, or materially expanded governance that
  remains compatible with existing principles.
- **PATCH**: clarification or correction that does not alter required behaviour.

**Compliance Review.** The constitution MUST be reviewed at least annually and after
material incidents, failed recovery exercises, platform-boundary changes, significant
agent-runtime or Spec Kit changes, or material legal, regulatory, or contractual
changes.

Constitution violations are critical findings. Specifications, plans, tasks, prompts,
architecture decisions, and runtime guidance cannot override this constitution.
